# Dashboard 多会话输出路由与分屏设计

日期：2026-08-08  
状态：已确认，待实施计划

## 1. 背景

Web Dashboard 的 `/chat` 页面通过 xterm.js 嵌入真实的 `hermes --tui`。当同一 TUI 连接中存在多个仍在运行的会话时，当前实现只完整渲染活动会话，并在事件入口丢弃其他 `session_id` 的显示事件。结果是多个输出源同时活跃时，用户无法稳定判断正在查看哪一路输出，也无法主动安排输出的显示优先级。

本设计在 Ink TUI 内增加多会话输出路由。第二个会话真正产生可显示内容时，Dashboard 自动提供“优先显示”或“分屏显示”的选择；分屏时最多显示两个会话，其余会话进入等待栏。Web Dashboard 继续嵌入同一套 TUI，不在 React 页面中重写聊天记录、输入框或 PTY。

## 2. 目标

- 多个独立会话同时输出时，不再争抢或混杂同一显示区域。
- 只在第二个会话实际产生可显示内容时提示用户，而不是仅根据活跃会话数量提示。
- 用户可以指定一个会话优先显示，也可以把屏幕划分为两个输出窗格。
- 分屏时只有焦点窗格可以输入，另一窗格只读并实时更新。
- 审批、澄清、sudo、secret 等控制请求保持全局可见，且优先级高于输出冲突选择。
- 第一版只在 Web Dashboard 的嵌入式 TUI 中自动启用，独立运行的 `hermes --tui` 保持现状。
- 不改变 Agent 核心、系统提示词、消息历史、提示词缓存或模型工具 schema。

## 3. 非目标

- 不在 Web React 前端创建多个 xterm、多个 PTY 或第二套聊天界面。
- 不把每个会话都改造成一套完整且永久驻留的 TUI 应用状态。
- 不在第一版提供超过两个同时可见的窗格。
- 不保存跨启动的默认输出优先策略。
- 不在非焦点窗格渲染原始推理文本；只展示状态、消息、工具和子代理摘要。
- 不自动将已完成窗格切换到其他仍在运行的会话。

## 4. 已评估方案

### 4.1 TUI 输出路由与双窗格渲染（采用）

在现有 Gateway 事件处理入口前增加 `OutputStreamRouter`。当前会话继续使用现有完整状态和渲染路径；非当前会话只维护有界的轻量显示缓冲区。用户将副窗格设为焦点时，通过现有 `session.activate` 把它提升为完整主会话。

该方案复用单一 PTY、单一 Gateway 连接、现有会话生命周期和 SessionDB，同时符合 Dashboard 必须嵌入真实 TUI 的架构约束。

### 4.2 Web React 管理多个 xterm/PTY（不采用）

该方案会在 Dashboard 层复制会话、输入和终端生命周期，增加多个 PTY 的资源占用，并形成第二套聊天控制器，违反现有架构约束。

### 4.3 为每个会话维护完整 TUI 状态（暂不采用）

该方案能让所有窗格独立交互，但需要拆分大量全局状态、计时器、浮层和输入逻辑，第一版风险和改动面过大。轻量缓冲区已能满足只读实时输出需求。

## 5. 总体架构

```text
GatewayEvent
    |
    v
OutputStreamRouter
    |-- 当前 session_id ----------> 现有 Gateway handler / TurnController
    |-- 非当前显示事件 ----------> 轻量 OutputStream buffer
    |-- 控制请求 ----------------> 全局 PromptZone
    `-- 第二路首次实际输出 ------> ConflictDetector
                                      |
                                      v
                              OutputConflictPrompt
                                      |
                         优先显示 / 分屏 / 暂不处理
```

核心组成：

- `outputStreamStore`：维护各会话的标题、状态、最后输出、未读数、有界缓冲区，以及当前布局和冲突周期。
- `OutputStreamRouter`：在现有活动会话过滤逻辑之前分类事件，并保证非当前事件不会误改当前 `TurnController`。
- `OutputConflictPrompt`：仅在 Dashboard 环境显示的一次性冲突选择器。
- `SplitOutputPane`：组合现有完整主 Transcript 与轻量只读副窗格。
- `OverflowBar`：显示第三个及更多等待输出流及其未读状态。

Dashboard 自动启用条件复用现有 `DASHBOARD_TUI_MODE` 常量；该常量由 PTY 启动器设置的 `HERMES_TUI_DASHBOARD` 解析得到，不增加新的用户配置或环境变量。

## 6. 状态模型

### 6.1 输出流状态

每个非当前输出流保存：

- `sessionId`
- `title`
- `status`
- `lastOutputAt`
- `unreadCount`
- `preview`
- 合并后的显示事件缓冲区
- 是否已结束、断开或被回收

显示缓冲区最多保留最近 200 个显示条目或约 64 KiB 文本，以先达到的限制为准。连续 `message.delta` 合并到同一消息条目。发生裁剪时，在顶部显示“更早输出已省略”，完整历史仍以 SessionDB 为准。

### 6.2 布局状态

- `single`：仅显示当前完整会话。
- `split`：显示当前完整会话和一个只读输出流。
- `tabs`：窄屏下使用与 `split` 相同的数据模型，只改变呈现方式。

最多两个会话可见。进入分屏时默认选择“当前焦点会话 + 最新产生输出的会话”；其他会话进入等待栏。新的输出不会自动替换已固定的副窗格。

### 6.3 冲突周期

冲突周期从第二个会话首次产生可显示输出开始，到并发输出会话数重新低于 2 时结束。

同一周期内：

- 冲突选择器最多出现一次。
- 选择优先显示、分屏或按 Esc 保持当前会话，均视为该周期已处理。
- 已处于分屏时不再显示冲突选择器。
- 会话完成不会自动切换焦点；窗格保留最终内容，同时提示其他会话仍在运行。

## 7. 事件分类

下列事件属于可显示输出，能够创建或更新非当前流，并可能触发冲突：

- `message.start`
- `message.delta`
- `message.interim`
- `message.complete`
- `tool.start`
- `tool.progress`
- `tool.complete`
- `status.update`
- `background.complete`
- 子代理 start/progress/complete 的摘要事件

仅发现多个活动会话、心跳、连接状态变化或没有用户可见内容的内部事件，不触发冲突选择器。

第一版不把原始 reasoning token 复制到副窗格。副窗格只显示“思考中”等状态，防止敏感内容泄露并减少渲染压力。

## 8. 交互设计

### 8.1 冲突选择器

选择器展示发生竞争的会话标题、状态和最近输出预览，并提供：

- 优先当前会话
- 优先新输出会话
- 选择其他等待会话
- 分屏显示
- Esc：本周期保持当前显示，不再提醒

不记录永久默认选项。下一次新的冲突周期重新询问。

### 8.2 宽屏与窄屏

- 终端宽度大于等于 110 列：左右双窗格。
- 小于 110 列：退化为标签页，一次显示一个窗格，但保留另一流的实时缓冲和未读状态。
- 宽度跨越阈值时只改变视图模式，不清空缓冲区、不改变焦点、不重新触发冲突。

每个窗格都有清晰的会话标题、运行状态和焦点标识。副窗格明确标注“只读”。

### 8.3 焦点与输入

任意时刻只有一个输入框和一个焦点会话。用户通过点击窗格、`Alt+Left`/`Alt+Right` 或 `/outputs` 切换焦点。

当只读副窗格获得焦点时：

1. 调用现有 `session.activate`。
2. 成功后用 SessionDB 返回的完整历史恢复该会话为主 Transcript。
3. 原主会话降为轻量只读副窗格，继续接收实时事件。
4. Composer 始终跟随当前完整会话。

激活失败时保持原焦点和布局，并显示非破坏性错误。

### 8.4 等待栏与 `/outputs`

第三个及更多会话显示在等待栏，包含标题、状态和未读数。`/outputs` 用于：

- 查看所有正在输出或等待的会话。
- 用等待会话替换副窗格。
- 切换焦点。
- 返回单窗格模式。
- 查看已结束但仍保留结果的输出流。

## 9. 控制请求优先级

界面阻塞优先级为：

```text
approval / clarify / sudo / secret
    > output conflict selector
    > composer
```

来自非当前会话的控制请求不能进入普通只读输出缓冲区。它们进入全局 `PromptZone`，并显示来源会话标题。响应必须携带原始 `session_id` 和请求 ID，确保答复回到正确会话。

同时到达多个控制请求时按到达顺序排队。存在控制请求时，输出冲突选择器等待；控制请求解决后再决定是否仍需展示冲突选择器。请求已过期时显示失效提示，不把响应发送到其他会话。

## 10. 生命周期与异常处理

- `session.activate` 失败：保持旧会话、旧焦点和旧布局。
- 会话结束：保持最终输出，不自动切换；状态标为完成。
- 会话被回收或关闭：缓冲区仍可查看，状态标为已结束。
- 断线重连：用 `session.active_list` 恢复标题和运行状态；主会话继续走现有历史恢复，非当前实时缓冲从重连后重新积累。
- 缓冲区溢出：裁剪旧内容并显示省略标记。
- 事件乱序：完成、失败、取消等终态一旦确定，迟到的 running 状态不能覆盖终态。
- 窗口缩放：只切换 split/tabs 呈现方式，不改变会话归属。
- 已在分屏：第三路输出仅进入等待栏，不弹出新的竞争选择器。

## 11. 性能策略

输出路由只复制用户可见的轻量字段，不复制完整 Gateway 事件历史。高频 delta 使用与现有流式输出相同量级的批处理节奏合并刷新，避免每个 token 都触发整个双窗格重绘。

主窗格继续沿用现有 `TurnController`、消息历史和渲染路径。副窗格使用专用只读条目组件，不初始化 Composer、审批状态、完整 Agent 状态或额外 Gateway 连接。

## 12. 预计代码改动

改动集中在 `ui-tui`：

- 新增 `src/app/outputStreamStore.ts`：输出流、布局、等待栏和冲突周期状态。
- 新增 `src/app/outputStreamRouter.ts`：事件分类、路由和冲突检测。
- 新增 `src/components/outputConflictPrompt.tsx`：冲突选择器。
- 新增 `src/components/splitOutputPane.tsx`：宽屏双栏和窄屏标签呈现。
- 调整 `src/app/createGatewayEventHandler.ts`：在当前会话过滤前路由事件。
- 调整布局、浮层、接口和主应用组合代码，接入全局控制请求及输出选择器。
- 扩展会话激活流程，使焦点切换保持失败原子性。
- 增加 `/outputs` 命令和快捷键处理。

现有 Gateway 事件已经携带 `session_id`，并已有 `session.active_list` 与 `session.activate`，预计不需要新增 Python RPC。若实施时发现某个现有事件缺少稳定的来源 ID，只允许做最小协议补全，不扩展 Agent 或模型工具表面。

## 13. 测试计划

### 13.1 纯状态与路由测试

- 仅第二路实际显示事件触发冲突；单纯存在多个活动会话不触发。
- 同一冲突周期只提示一次，并在并发降到 1 后允许下一周期再次提示。
- Dashboard 环境启用，独立 TUI 不改变行为。
- 当前会话事件仍走原处理器，非当前事件只更新对应缓冲区。
- 第三路及更多输出进入等待栏，未读数和最新预览正确。
- 200 条/64 KiB 限制、delta 合并和省略标记正确。
- 终态不会被迟到的运行状态覆盖。
- 高频 delta 在批次内合并刷新。

### 13.2 组件与交互测试

- 110 列显示双栏，109 列显示标签，跨阈值往返不丢状态。
- 只有焦点窗格拥有 Composer；副窗格显示只读标记。
- 点击、快捷键和 `/outputs` 能切换焦点或替换副窗格。
- 激活成功恢复完整历史；激活失败保持原布局。
- 当前流完成后不自动切换；其他流继续更新。
- 控制请求优先于冲突选择器，并响应到正确 `session_id`。
- 多个控制请求按顺序处理；过期请求不会误响应。
- 重连后恢复活动会话元数据，且主会话历史不回退。

### 13.3 回归与人工验证

运行：

```bash
cd ui-tui
npm test
npm run typecheck
npm run lint
npm run build
```

在 Dashboard 中创建两个或更多仍在运行的会话，安排交错输出，人工验证：

- 冲突选择器出现时机和单周期一次语义。
- 优先显示、宽屏分栏、窄屏标签和等待栏。
- 焦点切换、输入归属和完整历史恢复。
- 审批/澄清请求的全局优先级与来源标识。
- 会话完成、断线重连和窗口缩放行为。

## 14. 验收标准

- 多会话输出不会混杂、覆盖或争抢同一显示区域。
- 第二路实际输出出现时，Dashboard 自动提供优先显示或分屏选择。
- 同一冲突周期选择器最多出现一次。
- 最多两个会话可见，其余会话始终可从等待栏找到。
- 任意时刻只有一个可输入的焦点会话。
- 切换焦点后主窗格展示目标会话的完整、正确历史。
- 当前流结束后不自动抢占或切换焦点。
- 控制请求始终可见，并被发送回正确会话。
- 独立 `hermes --tui` 的默认行为不变。
- 不新增核心模型工具、系统提示词片段、用户配置环境变量或 Web React 聊天实现。
- TUI 类型检查、测试、lint 和构建通过。
