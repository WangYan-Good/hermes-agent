# Hermes 功能全景与进阶学习指南设计说明

**日期：** 2026-08-08  
**盘点基线：** `develop` 分支提交 `1a9a9c1fe`  
**目标读者：** Hermes 最终用户、部署运维人员、二次开发者和项目贡献者

## 1. 目标

为当前 Hermes Agent 项目建立一套中文分层文档，使读者既能找到完整的产品能力，又能沿着可验证的路线从“会使用”进阶到“理解原理、能够扩展和贡献代码”。

文档需要解决四个问题：

1. Hermes 当前能做什么，能力通过哪个入口提供。
2. 不同角色应该以什么顺序学习，前后知识如何依赖。
3. 核心能力为什么这样设计，运行时数据如何流动。
4. 学完每个阶段后，读者如何通过实验确认自己真正掌握了内容。

## 2. 范围与完整性标准

“所有功能”按用户可感知的**功能族**盘点，不在总览中逐项复制每个参数、模型名或技能正文。动态且数量较大的目录通过完整索引和现有参考文档承接，避免文档一经合并便失真。

功能清单必须覆盖以下范围：

- 交互入口：经典 CLI、Ink TUI、Web Dashboard、Electron Desktop、消息网关、OpenAI 兼容 API、ACP、Python 集成和批处理。
- 智能体核心：Agent Loop、模型与提供商解析、API 模式、提示词组装、工具调用、流式输出、中断、预算、目标与交付模式。
- 上下文与持久化：项目上下文文件、`@` 引用、会话、SQLite/FTS5、记忆、外部记忆提供商、上下文压缩、提示词缓存、轨迹和检查点回滚。
- 工具能力：文件、终端、浏览器、Web、视觉、音频、图像与视频、桌面控制、代码执行、委派、定时任务、搜索、项目、技能、MCP，以及按环境门控的集成工具。
- 自动化与协作：Cron、批处理、后台任务、子智能体、Mixture of Agents、Kanban、Hooks、中间件、Webhook 和消息投递。
- 通信渠道：核心与插件形式提供的全部消息平台，以及语音、媒体、线程、反应、流式回复和权限差异。
- 扩展体系：技能、技能包、Curator、插件类型、MCP、模型提供商、工具提供商、平台适配器和桌面插件 SDK。
- 配置与个性化：配置、密钥、Profiles、模型路由、回退、凭据池、Personality、`SOUL.md`、Skins、Pets 和项目工作区。
- 安全与运维：审批、配对、作用域、沙箱和远程执行环境、网络出口、密钥源、诊断、日志、监控、备份、迁移、升级与恢复。

每个功能族至少记录：

- 能力说明与典型使用场景；
- 面向用户的入口和必要前置条件；
- 所属子系统及核心源码入口；
- 一句话工作原理；
- 对应的现有详细文档或参考索引；
- 成熟度或约束，例如实验性、平台限定、凭据门控或可选插件。

完整性以“功能族全部覆盖 + 动态目录全部可追溯”为验收标准，而不是冻结模型数、工具数、插件数或技能数等易变计数。

## 3. 文档结构

正式交付位于 `docs/learning/zh-CN/`，采用一个入口和五篇主题文档：

1. `README.md`：阅读入口、角色导航、系统全景、文档基线与维护约定。
2. `01-feature-inventory.md`：按功能域组织的完整功能清单与证据索引。
3. `02-user-learning-path.md`：最终用户和部署运维人员的渐进式路线。
4. `03-developer-learning-path.md`：二次开发者与贡献者的源码学习路线。
5. `04-core-principles-and-labs.md`：核心运行原理、数据流和最小实验。
6. `05-progressive-projects.md`：五个从使用到扩展的递进实战项目。

入口文档负责回答“我该从哪里开始”；功能清单回答“项目有什么”；两条路线回答“按什么顺序学”；原理实验回答“为什么以及如何验证”；实战项目回答“如何把知识组合起来”。各文档通过相对链接互相引用，不复制大段内容。

## 4. 学习路径设计

两类读者共享基础阶段，然后按目标分流，并允许在高级阶段重新汇合。

### 4.1 共享基础

- L0：安装、Provider 设置、首次对话、配置目录和基本安全边界。
- L1：CLI/TUI、工具调用、上下文文件、会话、记忆、技能和 MCP 的使用心智模型。

### 4.2 用户与运维路线

- L2：自动化任务、消息网关、语音与媒体、Web Dashboard 和 Desktop。
- L3：Profiles、模型路由、回退与凭据池、权限、网络出口、日志、备份和升级。
- L4：面向个人或团队的可靠部署、故障恢复和多渠道运营。

### 4.3 开发者与贡献者路线

- L2：`AIAgent` 调用、Agent Loop、消息格式、Prompt Builder、Tool Registry 和 SessionDB。
- L3：模型 Provider、工具、技能、MCP、平台适配器与插件扩展。
- L4：缓存不变量、角色交替、上下文压缩、并发与投递可靠性、安全边界、E2E 测试和贡献规范。

每一级都必须提供“先修知识、学习目标、原理讲解、推荐阅读、源码入口、动手实验、验收标准和常见误区”。时间估算只作为建议，不作为掌握标准。

## 5. 核心原理教程

原理篇按运行数据流组织，而不是按文件树组织：

```text
用户输入
  → 客户端或平台适配器
  → 会话解析与权限检查
  → 稳定的系统提示词和历史消息
  → Provider/API 模式适配
  → 模型返回文本或工具调用
  → Tool Registry 分发与安全门控
  → 工具结果回到消息循环
  → 持久化、流式呈现和可靠投递
```

教程重点解释：

- 为什么提示词缓存要求对话期间系统提示词字节稳定；
- 为什么消息必须保持严格角色交替；
- 为什么 Hermes 采用窄核心、边缘扩展的 Footprint Ladder；
- 工具自动发现、工具集选择和 `check_fn` 门控如何控制模型工具面；
- 上下文压缩如何在保留首段、近期尾部和摘要之间权衡；
- SessionDB、FTS5、记忆文件和外部记忆提供商的职责边界；
- CLI、Gateway、TUI、Dashboard 和 Desktop 如何复用同一智能体核心，又保持不同交互面；
- 审批、配对、沙箱、网络出口和密钥管理如何形成分层安全边界；
- Cron、委派、Kanban、Hooks 和消息投递如何处理异步性、失败和恢复。

## 6. 递进实战项目

实战按风险和扩展面递增：

1. **个人项目助手**：使用上下文文件、会话、记忆和检查点完成一次可回滚的代码任务。
2. **定时简报**：组合 Web、技能和 Cron，理解新会话执行与结果投递。
3. **多渠道团队助手**：配置一个消息平台、权限、Profiles、日志和备份。
4. **CLI 命令 + Skill 扩展**：遵循 Footprint Ladder，在不增加核心工具的情况下扩展能力。
5. **独立 Plugin 或 MCP 服务**：实现门控能力、测试真实加载路径，并验证不会破坏核心缓存和工具面约束。

每个项目包含目标、架构、前置条件、操作步骤、预期现象、故障注入、验收清单和进一步挑战。涉及凭据的实验只描述配置键与安全做法，不要求在文档中展示真实密钥。

## 7. 证据与可维护性

功能描述优先引用以下事实来源：

1. 注册表和入口代码，例如 `hermes_cli/commands.py`、`hermes_cli/subcommands/`、`tools/registry.py`、`toolsets.py` 和各类插件清单。
2. 运行时核心代码，例如 `run_agent.py`、`model_tools.py`、`agent/`、`hermes_state*.py`、`gateway/`、`tui_gateway/` 和客户端目录。
3. 现有参考与开发者文档，例如 `website/docs/reference/`、`website/docs/user-guide/` 和 `website/docs/developer-guide/`。

维护规则：

- 易变清单不在多个位置手工复制；主文档链接到单一参考来源。
- 数量只作为带日期的盘点快照，不写成行为契约。
- 每项功能必须至少有一个代码入口或现有详细文档作为证据。
- 无法从当前代码或文档证实的能力不写入清单。
- 对插件、实验能力和平台限定能力明确标注边界。

## 8. 验证方案

文档完成后执行以下验证：

1. 检查六个目标文件均存在且相对链接可解析。
2. 从 CLI 子命令、斜杠命令、工具集、功能页、消息平台页和插件清单反向抽样，确认每类都有功能清单归属。
3. 检查文档中的源码路径在当前基线存在。
4. 检查示例命令与 `--help` 或现有参考文档一致。
5. 扫描 `TODO`、`TBD`、空章节和未解释缩写。
6. 检查教程没有把非秘密配置引导到 `.env`，没有建议绕过审批或安全边界。
7. 检查学习路线的每一级都有可运行实验和明确验收标准。

## 9. 非目标

- 不逐字翻译整个英文官网。
- 不复制所有命令参数、工具 Schema、插件配置和技能正文。
- 不新增或修改 Hermes 运行时功能。
- 不把第三方产品集成进核心，也不改变现有插件边界。
- 不把当前文件数、插件数或模型数写成永久不变量。
